# Erratum: v0.29.0 — preserved-file skew: update re-render and closeout-gate claims

> **Status:** staged for injection into the next release's migration note.
> When creating the next migration note, include a "Corrections to prior
> releases" section with the content below, then delete this file and
> dismiss the corresponding erratum card in `.local/coordinator/tasks/`.

## What was wrong

The v0.29.0 migration note (`templates/migrations/v0.29.0.md`) implicitly
promised that `update` advances the decision-record cohort together. Two
claims are falsified at runtime for an adopter holding a locally-edited
(preserved) `platform_managed` file in that cohort — most importantly
`state-lib.js`, where the release's retention gate lives. Preservation is
per file (the origin-hash three-way check in `internal/substrate/apply.go`
preserves each diverged file independently), not per cohort: `update`
re-renders the sibling docs/schema while a preserved `state-lib.js` keeps
its pre-gate base. Fact base:
`researches/sources/2026-11-05-origin-hash-stale-preserve-skew.md`.

### 1. "What `update` handles for you" — cohort-wide re-render claim (lines 56–59)

**Claimed (lines 56–59):** "Re-renders `state-lib.js`, the task-card schema
(v3 anyOf branch), the `task-closeout` / `task-delete` command docs,
`CLOSEOUT_TEMPLATE.md`, and `RECORD_LIFECYCLE.md` with the decision-record
preservation contract."

**Actual behavior:** the re-render applies per file. If `state-lib.js`
carries a local edit (live bytes diverged from the recorded origin hash),
`update` PRESERVES it (`managed-diverged`, reason `consumer-edit`) — the
schema and docs DO advance in the same update while the preserved script
keeps its old base. For such an adopter the note's sentence is false for
exactly the file that carries the runtime gate. The rollback section of
the same note (caveat (a), lines 106–110) already knew gate presence is
render-bound ("the corpus reverts with it — the preservation gate
disappears"); that knowledge was never applied to the preserved-file
update path.

### 2. Watch-out 1 — unconditional closeout-refusal claim (lines 69–73)

**Claimed (lines 69–73):** "The first `/task-closeout` after update refuses
a closeout that lacks the fenced block."

**Actual behavior (for an adopter with a preserved `state-lib.js`):** the
retention gate's runtime enforcement is JS-only — it lives in the rendered
`state-lib.js` (the Go binary never enforces closeout/retirement). When
`update` preserves a pre-v0.29.0-base `state-lib.js`, the closeout
refusal NEVER FIRES: the updated schema will structurally accept v3
records and the updated docs demand the block, but nothing refuses a
closeout lacking it and nothing verifies retirement carriers. The
documented gate has zero runtime enforcement in that state. (Caveat: the
hashes prove missing platform bytes, not which behavior is absent — a
preserved base that already carried the gate keeps it. The skew risk is
real precisely when the preserved base predates the gate.)

### Surfacing (post-v0.29.0)

On the v0.29.0 binary this state surfaces only as the generic
`preserved/stalled … [consumer-edit]` listing — it does NOT name the
functional consequence, and `doctor` reports it as non-failing
`consumer-preserved edit(s)` INFO. Dedicated surfacing ships with the
release that lands the cohort-skew fix (after v0.29.0): `update` then
marks a both-moved preserved path `[consumer-edit,
platform-also-changed]` with a stale-preserve warning, and `doctor`
reports `preserved-stale-vs-corpus` at WARN (doctor stays HEALTHY). Until
running such a binary, treat any preserved cohort file as potentially
behind the platform.

## Correction / runbook

Reconcile any preserved file in this cohort before relying on the
documented gate: safeguard the local edit FIRST (byte-for-byte backup —
`accept-platform` is destructive-by-intent and must never run bare on a
stale-preserved path before the edit is safeguarded), inspect what the
platform changed, then either adopt the platform version
(`vh-agent-harness accept-platform <path>`) and re-apply the local edit,
or port the customization into an overlay pack. Full procedure:
`docs/ai/preserved-managed-reconciliation.md` (in the vh-agent-harness
repository).

## Impact

Medium for adopters holding a locally-edited `state-lib.js` (the exact
reporting adopter class): the v0.29.0 docs describe a gate their runtime
does not enforce, and no v0.29.0-binary surface names that state beyond
the generic preserved-file listing. Decision records may be lost at card
retirement in that state because the verification the note promises never
runs. The defect is doc-vs-runtime truth, not data loss by the update
itself: preservation is intended behavior (the consumer edit is never
clobbered). Releases after v0.29.0 that carry the cohort-skew surfacing
fix close the visibility half at creation time (update warning) and
detection time (doctor WARN).
