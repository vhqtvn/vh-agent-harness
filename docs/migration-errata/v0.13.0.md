# Erratum: v0.13.0 — manifest ownership, placeholder SHAs, and README.agent.md re-render claims

> **Status:** staged for injection into the next release's migration note.
> When creating the next migration note, include a "Corrections to prior
> releases" section with the content below, then delete this file and
> dismiss the corresponding erratum card in `.local/coordinator/tasks/`.

## What was wrong

The v0.13.0 migration note (`templates/migrations/v0.13.0.md`) made three
false claims: two about the ownership and seeding of the
`.vh-agent-harness/release-defer-dispositions.json` manifest (sections 1–2),
and one about `README.agent.md` being a rendered artifact (section 3).

### 1. Ownership class — "seeded `platform_managed`" (line 12)

**Claimed (line 12, table row for commit `38c5c47`):** the manifest is
"seeded `platform_managed`" — i.e. the renderer seeds it from a template
and reconciles it on every `update`, the same lifecycle as the evaluator
script.

**Actual behavior:** no template exists for
`.vh-agent-harness/release-defer-dispositions.json` (confirmed: zero matches
under `templates/`). The file is fully UNMANAGED by the renderer — never
seeded on install, never reconciled by `update`, never in `lineage.yml` /
`rendered-outputs.json`. It is runtime-committed by the releaser agent as
the single manifest-only commit M in the release ceremony. This is
structurally identical to the coordinator-adoption marker
(`.vh-agent-harness/coordinator-adoption.json`) introduced in v0.16.0:
git-tracked, unmanaged, runtime-created, never renderer-seeded.

### 2. Placeholder handshake SHAs (line 30)

**Claimed (line 30, "What `update` handles for you"):** "Seeds the
`release-defer-dispositions.json` manifest template for fresh installs of
the release overlay (schema v1; the seed carries placeholder handshake SHAs
that the releaser recomputes at each release-prep)."

**Actual behavior:** there is no seed/template at all. The live file
carries REAL handshake SHAs (e.g. `evaluated_commit` /
`manifest_parent_commit` = the actual commit the releaser evaluated;
`evaluated_tree` = the actual tree SHA). These are never placeholders —
they are recomputed by the releaser at each release-prep from the real
commit graph, then committed. A fresh install has NO manifest until the
releaser creates it during the first release ceremony.

### 3. README.agent.md "re-rendered by update" claim (lines 5, 21, 27, 60)

**Claimed (lines 5, 21, 27, and 60 of `templates/migrations/v0.13.0.md`):**
`vh-agent-harness update` re-renders `README.agent.md` (specifically its
release-ceremony section). Line 21 states it directly ("re-renders
README.agent.md release ceremony"); line 27 restates it under "What `update`
handles for you" ("Re-renders `README.agent.md` with the single
release-authority model"); lines 5 and 60 each state or imply the same — that
`README.agent.md` is a rendered artifact whose release-ceremony section is
reconciled by `update`.

**Actual behavior:** `README.agent.md` is HAND-MAINTAINED, not a rendered
artifact. There is no `README.agent.md.tmpl` under `templates/core/`, and the
file is absent from the corpus ownership map (it carries no render ownership
class — not `platform_managed`, not `overlay_extension`, not any other). A
plain render may only overwrite `platform_managed` (and active
`overlay_extension`); everything else is preserved. `update` therefore
PRESERVES `README.agent.md` — it does not re-render it. Changes to
`README.agent.md` land via direct `docs(readme):` commits, exactly as this
repo's non-negotiable rule ("`README.agent.md` must always be up-to-date ...
any change ... MUST be reflected there in the same change") requires: the
maintainer edits it directly, the renderer never touches it.

**F3 class (§4.3):** released doc claiming unexecuted behavior. The note
asserts `update` performs a re-render the renderer structurally cannot
perform (no template exists to render from). An operator who trusts the note
would expect `update` to refresh `README.agent.md`'s release-ceremony section
after a binary self-update; it does not, and the section stays as the last
direct edit left it. This is the same defect class as sections 1–2 (a released
note describing a non-existent render/seeding path), now extended to a third
artifact.

## Impact

Low for release correctness. The release gate reads the committed manifest
via `HEAD:<path>` (committed blob) and validates the handshake SHAs against
the real commit graph regardless of how the file was created. The false
"seeded `platform_managed`" / "placeholder SHAs" claims describe a
non-existent template path; they do not affect the fail-closed gate
behavior or the override ceremony (which binds to the committed blob SHA).
The practical risk is operator confusion: an operator who believes a
template seeds the manifest may expect a fresh install to carry a manifest
and may not realize the releaser must create it from scratch on first
release. The correct mental model is "the releaser owns the manifest
end-to-end, from first creation through every recompute" — same as the
adoption marker's "the producer owns the marker from first write."

Low for release correctness, and low for the README-render claim as well.
The claim does not affect any gate or ceremony: `README.agent.md` was already
hand-maintained at v0.13.0 (it carried the correct release-ceremony section
because a maintainer edited it directly), and `update` preserving it is the
correct behavior, not a defect. The practical risk is operator confusion
symmetric to sections 1–2: an operator who believes `update` re-renders
`README.agent.md` may expect a binary self-update to refresh its
release-ceremony section automatically, then be surprised when only a direct
`docs(readme):` edit changes it. The correct mental model is "`README.agent.md`
is hand-maintained end-to-end; `update` never touches it."
