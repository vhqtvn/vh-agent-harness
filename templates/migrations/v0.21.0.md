# Migration: v0.21.0

## Summary
- **Release class:** MINOR (semver compatible). This release ships two
  consumer-relevant changes.
- **Upgrade path:** binary self-update, then re-render the corpus. Run
  `vh-agent-harness update --dry-run` FIRST to preview the three new skill
  directories before applying. Fully automatic for the default consumer;
  opt-out is a one-line `features:` change for consumers who do not want them.
  Unfloored adopters who relied on `--sandbox=off` must add an explicit
  `exec_sandbox.min_mode: off` before updating (see Watch-out #6).
- **Risk:** low for the default consumer. The opt-out pilot distribution is
  additive and INFORMS-only. The exec-sandbox absent-floor safety fix is a
  **deliberate behavior change for unfloored adopters** (see Watch-out #6): an
  explicit `--sandbox=off` that previously ran uncontained is now refused. This
  is the intended safety close, not a regression — but unfloored consumers who
  depended on the silent pass-through must take the one-line opt-out action.

### 1. exec-sandbox absent-floor safety fix (the safety priority of this release)
The exec-sandbox Level-B grant ships to every consumer via the core corpus,
but `run-shape.yml` is project-owned, so the harness cannot ship an
`exec_sandbox.min_mode` floor with the grant — **every adopter is unfloored by
default** until they add `exec_sandbox.min_mode`. Previously, an absent floor
and an explicit caller downgrade `--sandbox=off` collapsed to the same
"containment off" state, so an unfloored adopter running `--sandbox=off`
executed **fully uncontained** (fail-open). This release distinguishes absent
from explicit-off and **refuses** an explicit `--sandbox=off` when no floor
resolves anywhere in the chain (silence is not consent to disable
containment) — **fail-open → fail-closed**. The no-flag default
(best-effort, contained) and explicit stricter modes are unchanged; an explicit
`min_mode: off` (a deliberate opt-out) still honors `--sandbox=off`. This is a
semver-compatible safety hardening, not a breaking API change: the only
consumers affected are unfloored adopters who explicitly passed `--sandbox=off`,
who must now declare that intent via `exec_sandbox.min_mode: off`. Doctor gained
advisory check #22 `exec-sandbox-floor` (WARNs when the grant is carried but no
floor resolves — advisory only, never fails doctor). The corrected safety
framing: the grant ships unfloored-by-default; the refuse + the strict seed for
new installs + the doctor WARN are the layered close.

### 2. opt-out pilot distribution (default-on shipped pilots)
Three skills-only overlay pilots that previously required explicit selection
via `overlays:` now ship **default-on** for every consumer, disable-able via
the existing `features:` map. The pilots are `formal-verification-pilot`,
`resolve-first-pilot`, and `contract-invariant-audit-pilot`. They are strictly
**INFORMS-only** (skills only — no agent, command, permission, or gate), so
default-on distribution changes REACH, not authority: every consumer already
had the option to select these packs by name; default-on merely removes the
opt-in step. The mechanism reuses the existing `features:` map (platform-default
base ∪ project-wins per key) and a finite explicit feature→pack mapping table.
No profile, ownership-class, capability, or runtime change is required; the
default consumer gains three managed skill directories re-rendered
automatically by `update`. Last tag = `v0.20.0`; intended version = `v0.21.0`.

## How to migrate (automated)
```bash
vh-agent-harness self-update            # pull the new binary (v0.21.0)
vh-agent-harness version                # expect: 0.21.0 (<label>)
vh-agent-harness update --dry-run       # PREVIEW the 3 new skill directories first
vh-agent-harness update                 # applies platform_managed + active overlay_extension
vh-agent-harness doctor                 # lint the result
```

## Opting out (if you do not want the default-on pilots)
Add the feature keys to your `.vh-agent-harness/vh-harness-profile.yml`:

```yaml
features:
  formal-verification-pilot: false
  resolve-first-pilot: false
  contract-invariant-audit-pilot: false
```

Set only the pilots you want to disable to `false`; the rest stay on. After
editing, run `vh-agent-harness update` to re-render. An explicit
`overlays: [formal-verification-pilot]` entry re-adds the pack even when its
feature is `false` — the feature flag disables the default, not a forced
re-selection.

## What `update` handles for you
- Renders the three pilot skill directories as `overlay_extension` (the same
  ownership class as any explicitly-selected overlay pack):
  - `.opencode/skills/formal-verification/SKILL.md` (+ `references/`)
  - `.opencode/skills/resolve-first/SKILL.md` (+ `references/`)
  - `.opencode/skills/contract-invariant-audit/SKILL.md` (+ `references/` +
    `scripts/manifest-helper.js`)
- Adds the three pilot feature keys (default `true`) to the platform-default
  profile if they are not already present (schema-aware structural reconcile:
  your existing feature values are preserved; new platform keys are added).
- No profile, ownership-class, capability, or runtime change; no permission
  map change; no agent or command added.

## Watch-outs
1. **An active overlay may replace a differing same-path file.** If you
   previously had a project-local skill at the same path (e.g. you authored a
   `.opencode/skills/formal-verification/SKILL.md` of your own), the default-on
   pilot render will overwrite it IF your file is `overlay_extension`-owned.
   Run `vh-agent-harness update --dry-run` first to preview any overwrite. A
   project-local pack of the same name still shadows the embed wholly (it takes
   precedence at the render layer).

2. **Opting out stops future staging/management but does NOT auto-delete
   previously-rendered output.** If you set `features: <name>: false` after the
   pilot was already rendered, the skill files remain on disk, unmanaged (no
   future staging, no drift check). They are NOT automatically deleted. Opting
   out never makes a repo unhealthy: `doctor`'s managed-drift check only covers
   `platform_managed` paths, so the `overlay_extension`-owned pilot skill paths
   are outside its scope and a deselected pilot never produces a managed-drift
   failure. To regain visibility into which shipped pilots are enabled/disabled
   on disk, see the `doctor` shipped-pilots check added in this release.

3. **`--prune-orphans` does NOT remove opted-out pilot output.** The flag's
   orphan detection flags only files whose producing overlay SOURCE is now
   MISSING (the source file is gone from its pack, or the whole pack is gone).
   A merely-deselected pack's source still exists in the binary, so opting out
   produces NO orphan finding and `--prune-orphans` has nothing to prune for it.
   To remove opted-out pilot output, delete the skill directory manually, e.g.
   `rm -r .opencode/skills/formal-verification/` (verify every file in the
   directory belongs to the pilot before removing the directory). If you later
   re-enable the pilot, `update` re-renders the skill from the embedded source.

4. **OpenCode restart requirement.** After newly-rendered skills appear in
   `.opencode/skills/`, OpenCode must be restarted to discover them. A running
   OpenCode session caches the skill list per-process and will NOT see the new
   skills until restarted. This is a known OpenCode behavior, not a harness
   limitation.

5. **Source-checkout repos (this dev/dogfood repo).** Source-checkout consumers
   rebuilding locally MUST use `make update` (the `Makefile` target rebuilds
   the binary first), NEVER a bare `vh-agent-harness update` — the stale-embed
   guard refuses a live `update` when the embedded corpus differs from
   `templates/core/`. GoReleaser rebuilds for the published artifact regardless.

6. **exec-sandbox absent-floor behavior change (unfloored adopters).** The
   exec-sandbox Level-B grant ships with NO `exec_sandbox.min_mode` floor by
   default (`run-shape.yml` is project-owned, so the harness cannot ship a
   floor with the grant). Before this release, an absent floor + an explicit
   `--sandbox=off` collapsed to the same "containment off" state, so an
   unfloored adopter running `--sandbox=off` executed **fully uncontained**
   (fail-open). This release **refuses** an explicit `--sandbox=off` when no
   floor resolves anywhere in the chain. **If you are an unfloored adopter who
   relied on `--sandbox=off`, you have two options after updating:**
   - (Recommended) add a floor so containment is enforced, e.g. in
     `.vh-agent-harness/run-shape.yml`:
     ```yaml
     exec_sandbox:
       min_mode: strict
     ```
     then re-run — `--sandbox=off` will still be refused (the floor holds), and
     the no-flag default runs contained.
   - (Deliberate opt-out) if you intentionally want `--sandbox=off` to run
     uncontained, declare that intent explicitly so the refuse no longer fires:
     ```yaml
     exec_sandbox:
       min_mode: off
     ```
     An explicit `min_mode: off` is a deliberate opt-out and still honors
     `--sandbox=off`.
   The no-flag default (best-effort, contained) and explicit stricter modes
   (`--sandbox=strict`) are unchanged. Run `vh-agent-harness doctor` after
   updating — advisory check #22 `exec-sandbox-floor` WARNs when the grant is
   carried but no floor resolves, surfacing the gap without failing doctor.

## Rollback
Reversibility: binary downgrade + re-render. Install a prior `vh-agent-harness`
binary (e.g. `v0.20.0`), then `vh-agent-harness update` to re-render the corpus
from that binary's embedded corpus. The three pilot skill directories remain
on disk (unmanaged, not auto-deleted — see Watch-out #2; `--prune-orphans`
will not remove them either — see Watch-out #3) until removed manually. No
data migration; no irreversible state. Source-checkout consumers rolling back
MUST use `make update` against the prior tag, not a bare `update`.

## Non-consumer changes
The supporting work for this release includes the relocation of the three
pilot packs from project-local `.vh-agent-harness/overlays/` into the embedded
corpus `templates/overlays/` (content-preserving moves, no behavior change in
that step), the finite feature→pack mapping table and render-time feature
reconciliation logic, the selection tests, and the lifecycle-canon documentation
addition (the "shipped default-on overlay pilot" middle tier in the skill
lifecycle management decision memo). None of these are consumer-visible
behavior beyond the default-on activation described above.
