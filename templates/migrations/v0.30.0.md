4. **Review panel grows a 5th seat and a roster config.** After update +

   unchanged behavior plus one seat.
5. **If you PRESERVED `state-lib.js` on an older base** (edited or not),

6. **Staged errata are now release-gated.** From this release on, an erratum

## Rollback
A minor release is reversible by binary downgrade + re-render: reinstall
the `v0.29.0` binary and `vh-agent-harness update` (source-checkout repos:
`make update` against the prior tag). No data migration ran. **Caveats:**
(a) the corpus reverts with it — cohort refusal, doctor #28, stale-preserve
surfacing, the 5th seat/roster, and the eslink successor parser disappear;
(b) if you updated past a cohort refusal using `--allow-broken-cohort`,
the broken cohort edges remain broken after rollback — re-run the older
binary's `update --dry-run` and reconcile explicitly; (c) `state-lib.js`
normalization reverts with the corpus — a preserved older hub that you
reconciled against v0.30.0 expectations will again diverge from the
platform source (re-run the reconciliation runbook before re-updating);
(d) origin-hash ledger entries advanced by v0.30.0's `update` are
repo-local preserved state — under the older binary they may surface as
managed-drift; that is the ledger honestly reporting the downgrade, not a
defect; (e) local task cards mutated through the repaired coordination
substrate (restage transitions, serialized deletions) are gitignored
transport — the older substrate reads them but without the repaired
semantics; (f) operator-owned config files are not render output and
survive both directions untouched. No other state to undo.

## Errata for v0.29.0

## What this notices, and why (grammar-only intent)

The hub script `state-lib.js` carried exactly one token that does not
conform to the frozen ESM grammar the platform's link checker (eslink)
enforces: an update operator (`i++`) in a for-update slot. The change is
**grammar-only in intent** — it exists so the hub module parses FIT under
that grammar and its import/export edges become link-checkable.
No behavior change is claimed, and none is verified by the gates.

At landing
(measured receipt: `researches/sources/2026-11-09-eslink-stage4-candidate-measurement.md`
@ `f2c3700`; decision record:
`researches/decisions/2026-11-09-eslink-o4-stage4-normalization-option2.md`),
the one-token normalization flipped the hub module to FIT with 73 named
exports and recovered the 22 hub-blocked edges (19 incoming + 3 outgoing),
raising enforceable L3 link coverage from 10/49 to 32/49 with broken
remaining 0.

## The exact change (one token)

- File: `templates/core/.opencode/scripts/state-lib.js`, line **5554** —
  the file's sole update-op, in the **for-update slot of `fnv1a32Hex`**
  (the expression value is unused in that slot).
- Diff: `for (let i = 0; i < s.length; i++) {` →
  `for (let i = 0; i < s.length; i += 1) {` — i.e. `i++` → `i += 1`.
- Commit: **`4469f3c`** (post-v0.29.0 corpus work; line-anchored, one
  production file).
- Semantic-preservation receipts recorded at landing: an old-vs-new runtime
  vector probe of `decisionItemId` across the changed `fnv1a32Hex` loop
  returned **40/40 identical outputs** (recorded in the `4469f3c` commit
  message), and `make test-js` was green at landing and re-verified green
  at notice authoring (**234/234**, `node --test tests/scripts/*.test.js`).

## Hub origin-hash advance

`state-lib.js` renders as `platform_managed` into **every** consumer repo —
the core renderer ships it unconditionally. The one-token change therefore
advances the hub's recorded origin hash; the ledger sync landed at commit
`0b56ab6` (`.vh-agent-harness/origin-hashes.json`). Consequence by adopter
state:

- **Unedited hub (the default):** nothing to do. The next `update` performs
  the normal `platform_managed` overwrite and your hub matches the corpus.
- **Preserved or locally-edited hub:** your file does NOT advance
  automatically — see the next section.

## If you preserved or edited state-lib.js (stale-preserve consequence)

On the first `update` that carries this corpus change, a preserved hub is a
both-moved path (your bytes diverged from the recorded origin AND the
platform's bytes changed since that origin). You will see, per the landed
surfacing:

- the update listing marks the path
  **`[consumer-edit, platform-also-changed]`** and appends the
  **stale-preserve warning** — the preserved file did NOT receive this
  update's platform changes; dependent runtime files or documentation
  updated by this release may no longer match it;
- `vh-agent-harness doctor` reports the path as **`preserved-stale-vs-corpus`
  at WARN** (non-failing — doctor stays HEALTHY).

This is surfacing only: preservation is intended behavior, and your edit is
never clobbered. For this specific one-token change the platform delta is a
single grammar-conformance token, but the stale-preserve state itself is
what matters — a preserved hub keeps falling behind every subsequent hub
change until reconciled.

## Reconciliation — safeguard first, then reconcile

Before anything else, **back up and diff your local edit**: byte-for-byte
backup of the live file (e.g. `cp <path> <path>.bak`) and inspect the delta
with `vh-agent-harness diff`. Only then reconcile:
`vh-agent-harness accept-platform <path>` (destructive-by-intent — it
writes platform bytes and advances the origin) and re-apply your edit, or
port the customization to a canonical home (next section). Full procedure:
**`vh-agent-harness docs preserved-managed-reconciliation`**.

## Making the customization permanent (routes)

- **Additive customization** → an **overlay pack**: new paths only. A pack
  cannot replace a builtin at the same path — the render fails closed with
  `ErrShadowBuiltin`.
- **Same-path replacement** → raise the file to **`project_owned`** in
  `.vh-agent-harness/harness-ownership.yml` with a direct edit, then
  re-check and re-apply the platform delta each release (runbook options
  B1/B2 in `preserved-managed-reconciliation`).

## Errata for v0.29.0

## What was wrong

The v0.29.0 migration note (`templates/migrations/v0.29.0.md`) implicitly
promised that `update` advances the decision-record cohort together. Two
claims are falsified at runtime for an adopter holding a locally-edited
(preserved) `platform_managed` file in that cohort — most importantly
`state-lib.js`, where the release's retention gate lives. Preservation is
per file (the origin-hash three-way check in `internal/substrate/apply.go`
preserves each diverged file independently), not per cohort: `update`
re-renders the sibling docs/schema while a preserved `state-lib.js` keeps
its pre-gate base. Fact base:
`researches/sources/2026-11-05-origin-hash-stale-preserve-skew.md`.

### 1. "What `update` handles for you" — cohort-wide re-render claim (lines 56–59)

**Claimed (lines 56–59):** "Re-renders `state-lib.js`, the task-card schema
(v3 anyOf branch), the `task-closeout` / `task-delete` command docs,
`CLOSEOUT_TEMPLATE.md`, and `RECORD_LIFECYCLE.md` with the decision-record
preservation contract."

**Actual behavior:** the re-render applies per file. If `state-lib.js`
carries a local edit (live bytes diverged from the recorded origin hash),
`update` PRESERVES it (`managed-diverged`, reason `consumer-edit`) — the
schema and docs DO advance in the same update while the preserved script
keeps its old base. For such an adopter the note's sentence is false for
exactly the file that carries the runtime gate. The rollback section of
the same note (caveat (a), lines 106–110) already knew gate presence is
render-bound ("the corpus reverts with it — the preservation gate
disappears"); that knowledge was never applied to the preserved-file
update path.

### 2. Watch-out 1 — unconditional closeout-refusal claim (lines 69–73)

**Claimed (lines 69–73):** "The first `/task-closeout` after update refuses
a closeout that lacks the fenced block."

**Actual behavior (for an adopter with a preserved `state-lib.js`):** the
retention gate's runtime enforcement is JS-only — it lives in the rendered
`state-lib.js` (the Go binary never enforces closeout/retirement). When
`update` preserves a pre-v0.29.0-base `state-lib.js`, the closeout
refusal NEVER FIRES: the updated schema will structurally accept v3
records and the updated docs demand the block, but nothing refuses a
closeout lacking it and nothing verifies retirement carriers. The
documented gate has zero runtime enforcement in that state. (Caveat: the
hashes prove missing platform bytes, not which behavior is absent — a
preserved base that already carried the gate keeps it. The skew risk is
real precisely when the preserved base predates the gate.)

### Surfacing (post-v0.29.0)

On the v0.29.0 binary this state surfaces only as the generic
`preserved/stalled … [consumer-edit]` listing — it does NOT name the
functional consequence, and `doctor` reports it as non-failing
`consumer-preserved edit(s)` INFO. Dedicated surfacing ships with the
release that lands the cohort-skew fix (after v0.29.0): `update` then
marks a both-moved preserved path `[consumer-edit,
platform-also-changed]` with a stale-preserve warning, and `doctor`
reports `preserved-stale-vs-corpus` at WARN (doctor stays HEALTHY). Until
running such a binary, treat any preserved cohort file as potentially
behind the platform.

## Correction / runbook

Reconcile any preserved file in this cohort before relying on the
documented gate: safeguard the local edit FIRST (byte-for-byte backup —
`accept-platform` is destructive-by-intent and must never run bare on a
stale-preserved path before the edit is safeguarded), inspect what the
platform changed, then either adopt the platform version
(`vh-agent-harness accept-platform <path>`) and re-apply the local edit,
or port the customization to a canonical home — additive changes go to an
overlay pack (new paths only: an overlay can never replace a builtin at
the same path; the render fails closed with `ErrShadowBuiltin`), and
same-path replacement requires raising the file to `project_owned` in
`.vh-agent-harness/harness-ownership.yml` with a direct edit and a
re-checked, re-applied platform delta each release (runbook options
B1/B2). Full procedure:
`docs/ai/preserved-managed-reconciliation.md` (in the vh-agent-harness
repository).

## Impact

Medium for adopters holding a locally-edited `state-lib.js` (the exact
reporting adopter class): the v0.29.0 docs describe a gate their runtime
does not enforce, and no v0.29.0-binary surface names that state beyond
the generic preserved-file listing. Decision records may be lost at card
retirement in that state because the verification the note promises never
runs. The defect is doc-vs-runtime truth, not data loss by the update
itself: preservation is intended behavior (the consumer edit is never
clobbered). Releases after v0.29.0 that carry the cohort-skew surfacing
fix close the visibility half at creation time (update warning) and
detection time (doctor WARN).
