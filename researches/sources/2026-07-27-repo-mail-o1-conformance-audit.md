## Carrier architecture summary

vh-solara is two-tier. A **controller** (`pkg/server/daemon.go`) runs centrally: it accepts worker tunnel connections over WebSocket+yamux (`/vh-solara/ws`), serves the operator dashboard, and reverse-proxies browser requests to workers via raw byte proxying through yamux streams. A **worker** (`pkg/agent/daemon.go` + `pkg/web/server.go`) runs on each machine beside OpenCode: it dials back to the controller over WS+yamux and hosts the SPA plus a `/vh/*` HTTP surface that drives OpenCode (snapshot/stream/spawn/send/abort/archive), a backend-authoritative per-session message **queue** (`pkg/web/queue.go`), and an **alerts** engine (`pkg/alerts`) providing in-app notice, webhook, command-channel, and Web Push delivery. Auth (`pkg/auth`) is operator-session-based (OIDC/passphrase/trust-proxy) wrapping the worker mux, plus a bearer-gated coordination API front (`pkg/server/coordapi.go`) and a RegSecret on worker registration. Work-bearing state lives behind explicit `/vh/*` routes: the session queue, the aggregator's OpenCode-fed store (`pkg/aggregator`), the process manager (`pkg/procmgr`), and the OpenCode lifecycle (`pkg/oclife`).

Surfaces that matter for the audit: (a) controller proxy path `pkg/server/proxy.go` (raw byte proxying); (b) tunnel byte path `pkg/tunnel/websocket.go` + `pkg/tunnel/types.go`; (c) worker-side HTTP ingress chain `pkg/web/server.go:862-986` + middleware at `:985`; (d) auth model `pkg/auth/auth.go`; (e) alerts terminal-projection surface `pkg/alerts/{engine,dispatch,push}.go`; (f) work-bearing routes enumerated at `pkg/web/server.go:894-979`; (g) feature-mount mechanism `pkg/web/feature.go` + `pkg/web/server.go:224-227`.

## Property-by-property verdicts

### 1. Exact-byte preservation
- **Verdict: CONFORMS**
- Citations: `pkg/server/proxy.go:168` (`io.ReadAll(r.Body)` — body read verbatim); `pkg/server/proxy.go:220-222` (`yamuxW.Write(bodyBytes)` — exact bytes written to yamux); `pkg/server/proxy.go:236,254-300` (`runBidirectionalCopy` — pure `io.Copy` both directions); `pkg/agent/daemon.go:387-405` (worker-side `io.Copy(localConn, stream.Raw())` and `io.Copy(respW, localConn)` — verbatim); `pkg/tunnel/websocket.go:90-105` (`wsRWC.Write` → `websocket.BinaryMessage` — raw bytes); `pkg/tunnel/websocket.go:68-88` (`wsRWC.Read` — raw bytes).
- Basis: The request BODY flows through end-to-end as opaque bytes. The controller reads the full body into a byte slice (`io.ReadAll`) and writes that exact slice onto the yamux stream; the worker's `handleRawProxy` does pure `io.Copy` between the yamux stream and the local web port in both directions. Go's `net/http` does not auto-decompress or transcode request bodies (no `Content-Encoding` handling at the transport layer — confirmed: the only gzip code is application-level snapshot RESPONSE compression at `pkg/web/server.go:1297-1305`, explicitly documented as "not HTTP Content-Encoding" and "the controller raw-proxies the body verbatim"). Header case IS canonicalized by Go's `net/http` map (`pkg/server/proxy.go:214-218` re-emits from `r.Header`), but Contract A/C bind `integrity.content_digest` to the canonical message bytes (the body), not the HTTP envelope. No whitespace trim, JSON re-serialization, charset conversion, gzip-degzip, or body-touching header normalization exists on the path a relay ingress would use. (Caveat: `io.ReadAll` buffers the whole body in memory — a size concern, not a byte-preservation concern.)

### 2. E2E content confidentiality (MANDATORY per Decision 3)
- **Verdict: CONFORMS**
- Citations: `pkg/server/daemon.go:221-277` (`hostInterceptor` routes on host regex, never body); `pkg/server/daemon.go:102-178` (`buildRootHandler` — path/host/method routing); `pkg/server/coordapi.go:107-133` (`proxyToVH` — routes on method/path/query, not body); `pkg/web/views.go:466-481` (`dispatchView` matches on `r.URL.Path` only); `pkg/web/server.go:862-986` (mux pattern-based routing); `pkg/web/server.go:985` (middleware chain `securityHeaders(auth.Middleware(cors(csrfGuard(logRequests(stampMeta(dispatchView(mux)))))))` — none parse body).
- Basis: Every routing decision in the carrier is keyed off URL path, host, method, or headers — never off request body content. Body decoding (`json.NewDecoder(r.Body).Decode`) happens only INSIDE individual handlers after routing has resolved (e.g. `pkg/web/notes.go:112`, `pkg/web/archive.go:45`, `pkg/web/git.go:90`, `pkg/web/feature.go:191`), never to decide which handler runs. A relay module that routes on channel-id (carried in a path segment or header) and treats the body as opaque ciphertext is fully supported. The relay never needs to read body content to deliver; Decision 3 (E2E body encryption mandatory) is satisfied by construction.

### 3. Digest/authenticator carriage
- **Verdict: CONFORMS**
- Citations: `pkg/server/proxy.go:168,220-222` (body bytes passthrough — envelope fields ride inside untouched); `pkg/web/server.go:985` (no middleware rewrites body fields); `pkg/tunnel/websocket.go:90-105` (raw byte transport, no field inspection).
- Basis: The integrity fields (`integrity.content_digest`, `integrity.authenticator`) are elements of the canonical envelope, which is itself the opaque body bytes from the carrier's perspective. No surface on the proxy/tunnel/ingress path parses, strips, regenerates, or rebinds envelope fields — the body is an uninterpreted byte sequence from ingress to handler. The relay module reads envelope fields via its own application-level decode (inside its handler), exactly as `pkg/web/queue.go` reads `QueueItem` fields inside `handleQueueEnqueue`. Nothing in the architecture intercepts or rewrites those fields at the transport layer.

### 4. Channel-scoped directional authorization
- **Verdict: ADAPTABLE**
- Citations: `pkg/auth/auth.go:36-65` (Config modes: OIDC/passphrase/trust-proxy — operator identity, NO channel concept); `pkg/auth/auth.go:143-205` (Middleware — session-based operator gate); `pkg/server/daemon.go:58-69` (`coordFront` — precedent for a separately-authenticated front mounted before `Auth.Middleware`); `pkg/server/coordapi.go:74-86` (`checkAPIBearer` — bearer-gate precedent); `pkg/server/daemon.go:284-291` (`RegSecret` — worker-registration shared secret); `pkg/server/daemon.go:171,175` (Auth.Middleware then coordFront ordering — separate fronts compose).
- Basis: The existing auth model has ZERO per-channel directional concept — it authenticates the OPERATOR (email/passphrase) for the dashboard, a single bearer token for the coordination API, and a single RegSecret for worker registration. Contract B requires per-channel, per-direction keys with deny-first revocation. **The required change:** mount the relay ingress through a new front (mirroring `coordFront` at `daemon.go:58-69`) that applies channel-scoped directional auth before `Auth.Middleware`, then proxies to the worker's relay handler via the tunnel. This is a small, named addition that reuses the established "separate front before the session-auth edge" pattern. It does NOT weaken the existing operator-session auth (the `userMux`/dashboard still requires it) and does not introduce a shared unrestricted credential (each channel-direction gets its own key lifecycle, per Contract B).

### 5. Freshness/replay/idempotency
- **Verdict: CONFORMS**
- Citations: `pkg/web/feature.go:131-172` (`idemCache` — existing idempotency-key dedup precedent); `pkg/web/queue.go:297-318` (`recoverStaleDispatchingLocked` — existing replay/abandonment-recovery precedent, terminal-only, never re-dispatches); `pkg/server/proxy.go:33-240` (single-shot per request — no retry/redelivery); `pkg/agent/daemon.go:79-187` (reconnect loop — each reconnect is a fresh yamux session, not a frame replay); `pkg/web/server.go:106,349` (`idem` field — wired into feature handlers).
- Basis: `message_id` is preserved end-to-end as opaque body bytes (Property 1). The HTTP/proxy/tunnel layers do not silently replay or duplicate — each request opens a fresh yamux stream (`proxy.go:62` `OpenStream`) and is single-shot. The existing `idemCache` (`feature.go:131-172`) demonstrates the architecture's idempotency-key dedup pattern a relay module would reuse for per-channel replay detection, and `queue.go`'s stale-dispatch recovery demonstrates the terminal-state-only recovery discipline (transitions to `unknown`, never back to `pending`, never re-dispatches). The relay module maintains its own per-channel recipient state (uniqueness + expiry + optional sequence per Contract B); the architecture neither forces duplication nor strips identity.

### 6. Channel isolation
- **Verdict: CONFORMS**
- Citations: `pkg/tunnel/websocket.go:181-244` (`MuxTransport` — yamux streams are independently framed); `pkg/tunnel/websocket.go:228-244` (`OpenStream`/`AcceptStream` — each stream is an isolated bidirectional byte channel); `pkg/server/proxy.go:62,33-240` (one fresh stream per request — no cross-request stream reuse); `pkg/web/server.go` (handlers receive an independent `*http.Request` — no shared per-request state).
- Basis: Yamux multiplexes independent streams over one WebSocket; each request gets its own stream with no cross-stream content visibility at the transport layer. HTTP handlers are stateless per-request. A relay module keys its storage by `channel-id` (an opaque field the module reads from the envelope); the architecture imposes no cross-channel data sharing — storage isolation is the module's to enforce, and nothing in the carrier forces a leak. Operator-side logging (`daemon.go:357` worker registration; `proxy.go:50,262` request-path logging) records worker IDs and paths, but this is operator-observable metadata on the operator's own carrier — explicitly accepted by the threat model ("the relay MAY observe metadata") and not cross-participant visibility.

### 7. Terminal-only projection (Non-Actuation on the carrier side — the spine)
- **Verdict: CONFORMS**
- Citations: `pkg/web/server.go:862-986` (all routes are explicit `mux.HandleFunc` registrations — no auto-routing); `pkg/web/server.go:224-227` + `pkg/web/feature.go:99-124` (Feature mechanism — a relay module registers its own isolated routes with no forced wiring to work code); `pkg/alerts/engine.go:73-80` (`deliver` → `store.EmitNotice` + `dispatcher.Dispatch` + `pusher.Send` — terminal fan-out); `pkg/alerts/dispatch.go:58-93` (`Dispatch` → webhook POST, terminal); `pkg/alerts/push.go:129-157` (`Send` → RFC 8297 Web Push, terminal); work-bearing routes are explicit and disjoint: `pkg/web/server.go:896-946` (`/vh/archive`, `/vh/restart-opencode`, `/vh/restart-server`, `/vh/reload`, `/vh/reload-project`, `/vh/git/*`, `/vh/opencode/restart`, `/vh/session/{id}/queue`, `/vh/term/kill`).
- Basis: The carrier has NO architectural path that auto-routes an inbound request at one path to a work-bearing handler at another. Routing is path-explicit via the mux; a relay handler at e.g. `/vh/mail/inbox` is invoked ONLY for that path and contains whatever body the module author writes. A conforming relay handler stores the opaque message and projects to terminal surfaces via the alerts engine (`EmitNotice` for in-app inbox, `pusher.Send` for Web Push) — a pure read-and-notify path that never writes to OpenCode, spawns a session, or enters a work queue. The alerts engine is a one-way read→notify pipeline (it subscribes to the store and emits; it does not feed back into the aggregator or queue). Work-bearing surfaces (`/vh/spawn`, `/vh/send`, `/vh/abort`, queue verbs, `/vh/restart-*`, procmgr, oclife) are each behind their own explicit routes and are not reachable from a new ingress path without deliberate wiring the module author would have to add. (See Contradictions for the alerts command-channel nuance.)

### 8. No hidden connection to work-bearing state
- **Verdict: CONFORMS**
- Citations: `pkg/web/queue.go:793-806` (`queueRegistry.store` — reached ONLY via `/vh/session/{id}/queue` POST → `handleQueueEnqueue`); `pkg/aggregator/aggregator.go:679-759` (`Run` — fed exclusively by the OpenCode event tail + hydrate, not by HTTP ingress); `pkg/procmgr/procmgr.go:97-136` (`NewManager`/`Start` — reached via the managed-project Orchestrator + trust flow at `pkg/web/managed.go`, not via a generic ingress route); `pkg/oclife/oclife.go:121-265` (a state machine updated by the daemon's topology arm, not ingress-reachable); `pkg/web/server.go:410-464` (`aggFor` — aggregator resolution keyed by project dir, returns a read view; does not dispatch work); `pkg/web/server.go:894-946` (the enumerated work-bearing verbs are each isolated routes).
- Basis: Each work-bearing queue/state store has a single, explicit entry point that is NOT a generic ingress. The session queue is entered through `POST /vh/session/{id}/queue` only; the aggregator's store is populated by the OpenCode event stream, not by inbound HTTP; procmgr launches happen through the managed-project orchestrator's trust-gated flow; oclife transitions are driven by the daemon. None of these is reachable from a relay ingress handler unless the module author explicitly imports and calls them — the architecture wires no such hidden path. A relay module that stores to its own files (peer to `.vh-solara/sessions/<id>/queue.json`) and emits notices does not touch any work-bearing record.

### 9. Identity handling
- **Verdict: CONFORMS**
- Citations: `pkg/auth/auth.go:36-65,143-205` (auth resolves OPERATOR identity — email/passphrase/proxy-header — never repo identity); `pkg/server/daemon.go:315-357` (worker registration logs `WorkerID`/`WorkerName` — machine identity, not repo identity); `pkg/web/server.go:1027-1044` (`logRequests` — logs method/path/status/duration, NOT body or identity); `pkg/server/proxy.go:50,67,262` (logs method/path/errors, NOT body).
- Basis: The carrier has no concept of "repo identity" anywhere in its auth, routing, or logging surfaces — it knows operator identity (the dashboard user) and machine identity (the worker ID). A relay module operates on opaque `channel-id` values read from the envelope; the channel-id↔repo map lives in private deployment config the carrier code never reads (Contract B). The carrier does not force a real-identity lookup on the relay path, and its request logging records only method/path/status/timing — not request bodies or identity material. The module is free to log only opaque channel-ids; nothing in the architecture forces it to log, persist, or resolve a real repo identity.

## ADAPTABLE items — required changes (consolidated; one entry)

- **Channel-scoped directional auth front** (Property 4). Surface to change: `pkg/server/daemon.go:58-69` (the `coordFront` pattern) and `pkg/server/daemon.go:102-178` (`buildRootHandler` front-ordering). The change: add a new front (e.g. `mailFront`) mounted before `Auth.Middleware` (as `coordFront` is at `:175`), applying per-channel directional authentication (key-id lookup, deny-first revocation, per-direction key lifecycle per Contract B) to the relay ingress paths, then proxying to the worker's relay handler through the existing `Proxy.HandleWorkerDirect`. Why it does not break the service's existing purpose: it mirrors the already-established `coordFront`/`checkAPIBearer` pattern (`coordapi.go:58-86`), sits entirely outside the operator-session `Auth.Middleware` that still gates the dashboard/`userMux`, and introduces no shared unrestricted credential — it is an additive, separately-scoped auth front, not a weakening of the operator auth edge.

## Contradictions / ambiguity encountered

- **Alerts command-channel is an execution surface, but is operator-configured, not message-controlled.** `pkg/alerts/dispatch.go:87-88,124-133` defines `ChannelCommand`, which runs `exec.CommandContext(ctx, ch.Command, ch.Args...)` with the notice rendered as `VH_ALERT_*` env vars when a notice fires. This IS an `exec` path reachable from the alerts engine. However: (a) the command and args are entirely OPERATOR-configured in the operator's private alerts config (`alerts.jsonc`), not chosen or influenced by message content; (b) the comment at `dispatch.go:121-123` explicitly frames it as "the operator's own config, the same trust level as managed-project processes"; (c) the relay module is NOT required to wire to command channels — it can deliver via `store.EmitNotice` (in-app inbox) and `pusher.Send` (Web Push) alone, both unambiguously terminal. This is consistent with the spec's "operator is the sole bridge from information to action" — the command channel is a pre-configured operator bridge, not relay-authored actuation. Property 7 remains CONFORMS because the architecture PERMITS a module that does not actuate (the command channel is opt-in operator config, not a forced delivery path); but a downstream implementer MUST treat command-channel routing as operator-bridge territory and must not introduce relay delivery-rule vocabulary that selects or parameterizes commands.
- **No contradiction detected** on exact-byte preservation, E2E confidentiality, digest carriage, replay/freshness, channel isolation, work-bearing isolation, or identity handling within the checked scope. The carrier's routing/transport/storage surfaces are uniformly metadata-keyed and body-opaque.

## Gate verdict (restated)

**O1 VIABLE.** Every one of the 9 critical properties is CONFORMS (properties 1, 2, 3, 5, 6, 7, 8, 9) or ADAPTABLE (property 4, channel-scoped directional authorization — a small, named addition of a channel-auth front mirroring the existing `coordFront` pattern, which does not weaken the operator-session auth edge). No property is NON-ADAPTABLE: the carrier never forces a relay module to actuate (Property 7 spine holds — work-bearing routes are explicit and disjoint from any new ingress path, and the terminal-projection surface via `pkg/alerts` is a one-way read→notify pipeline), never requires reading message bodies to route or deliver (Properties 1–3 hold — routing is path/host/method-keyed, bodies flow as opaque verbatim bytes through `pkg/server/proxy.go` + `pkg/tunnel/websocket.go` + `pkg/agent/daemon.go`), preserves `message_id` and envelope fields untouched (Property 5), enforces per-stream isolation at the yamux boundary (Property 6), keeps work-bearing queues/stores behind their own explicit routes with no hidden ingress wiring (Property 8), and has no concept of repo identity to leak (Property 9). The single ADAPTABLE item is an additive auth front that mirrors an already-deployed pattern. The one ambiguity (alerts `ChannelCommand`) is operator-configured bridge territory, not a forced actuation path, and is flagged for the downstream implementer. O1 conforms on the carrier side; O2 need not be promoted to primary on architectural grounds.
